# 激活上下文看板生成指南 (active-context-guide.md)

## 01. 技能定位与生成目标

本指南用于指导 AI 在 `start-project` 阶段 2（或后续任务更新）时，读取 `docs/prd-and-design.md` 提取出的第一阶段 MVP 目标，**生成/更新激活上下文**：

- **单轨项目**：单一产物 `docs/active-context.md`（纯文本动态看板 / 滚动窗口）。
- **多轨项目**：`docs/active-context.md` 降级为**薄索引与路由表**，任务台账落到 `docs/context/<轨>.md`（判定与模板见 §04）。
- 看板形态：仅 MD；不生成/不维护 HTML 副本。
- C 类小任务不强制更新看板（除非碰里程碑），日末/发版统一收口。

---

## 02. 编写与生成原则

1. **无 Frontmatter**：本文件是项目文档（看板），不是 IDE 注入配置——顶部不写任何 YAML Frontmatter 元数据。
2. **目标聚焦（Sprint Focused）**：仅聚焦当前阶段（通常是 MVP 1.0 或第 1 个迭代周期）的核心功能，避免将远期规划混入当前上下文。
3. **状态可追踪（State Trackable）**：采用清晰的 Task Checklist 表达（`[ ]` 未开始, `[/]` 进行中, `[x]` 已完成）。
4. **单一产物（MD Only）**：只落盘 MD，不生成 HTML 或其它格式的副本。
5. **看板 = 当前窗口，不承载完成史**：看板只保留「当前焦点 / 下一步 / 未完成项」；**已完成节点只留一行里程碑**（可指向归档或变更日志），不逐条堆叠完成纪要——否则滚动窗口必然膨胀，最终把真正的上下文挤出去。历史明细进 `docs/archive/`（或项目自定的变更日志）。
6. **行数预算按「文件」计**：单轨文件 ≤100 行；多轨时**索引 ≤50 行**、**每份分轨文件 ≤100 行**。任一份超限 → 先归档完成史，再考虑拆轨。
7. **看板更新协议**：任务节点的收口更新按 `docs/PROJECT-RULES.md` §3 工作流的完成门禁执行；**C 类小任务不强制更新看板**（除非碰里程碑），日末/发版统一收口。
8. **【多轨】开工第一读 = 索引**：任何会话开工先读索引 → 在「角色 → 轨」映射里定位本轨 → **只读写本轨文件**。禁止跨轨直接编辑他人轨文件。
9. **【多轨】收口只写本轨**：本轨收口只改本轨文件；**跨轨依赖/阻塞一律登记到 `docs/tasks.yaml`**（不写进别人轨），由任务看板集中暴露。
10. **【多轨】任务状态只有一个源**：全量任务（含单轨内部）进 `docs/tasks.yaml` → 由脚本生成 HTML 看板；**轨看板不再抄任务清单**（只留「本轨目标 / 本轨下一步 / 本轨关键决策」）。一处维护、一处派生，才是防双写。

## 03. 单轨形态（单人 / 单责任线）

### 03.1 判定
轨道数 ≤1（一个负责人、一个可独立推进的目标域）→ 用单文件。**既有单轨项目不受多轨改造影响，保持现状。**

### 03.2 模板：`docs/active-context.md`

```markdown

- **版本阶段**：[如：MVP 1.0 基础原型 / Phase 1 核心功能开发]

- **关键交付物**：[如：可运行的后端 API + 前端登录/看板页面]

## 02. 任务清单与状态 (Task Kanban)
- [ ] **步骤 1: 基础设施与脚手架搭设**
  - [ ] 初始化项目基础结构与配置文件
  - [ ] 配置环境变量与本地依赖环境
- [ ] **步骤 2: 接口 Schema/DTO 定义与 Swagger 导出 (API-First 方案 A)**
  - [ ] 编写全局统一 `ApiResponse<T>` 范型响应结构与错误码
  - [ ] 编写核心 DTO / Schema 校验逻辑并导出 Swagger/OpenAPI
  - [ ] 配置前端基于 Swagger 的类型自动导出与开关式 Mock 环境
- [ ] **步骤 3: 核心逻辑与 UI/UX 界面实现**
  - [ ] 后端实现 Controller / Business Logic / Repository
  - [ ] 前端搭建页面组件并接入 Mock/真实数据流
- [ ] **步骤 4: 前后端联调测试与收尾**
  - [ ] 切换真实 API 联调与边界条件/异常处理校验
  - [ ] 核心流程冒烟测试通过

## 03. 关键决策与架构遗留 (Key Decisions & Context)
- **已做出的关键技术决策**：

  - [决策 2]：[如：统一使用 ApiResponse<T> 响应包装与 MSW 开关式 Mock]
- **风险与技术债记录**：

- **AI 交互指令提示**：后续会话可直接提示 “按照 active-context.md 的下一步继续执行”。

## 05. 规则自我演进维护
本文件为动态看板。每次完成任务节点或发生业务需求变更时，AI 必须按照 `docs/PROJECT-RULES.md` §3 工作流的更新协议，同步更新本文件（**仅 MD，不再生成/渲染 HTML 副本**）；C 类小任务不强制更新，日末/发版统一收口，确保任务状态与实际工程代码完美一致。
```

## 04. 多轨形态（≥2 条并行责任线）

> **触发时机**：项目出现第二个负责人、或同一仓出现第二个可独立推进的子项目/目录域时。**单轨项目不要预先多轨化**（无收益，只增加文件）。

### 04.1 什么算「一条轨」

**轨（track）= 一条可独立推进的责任线**，三条判据**同时**成立：

1. 有**独立的目录域**（互不重叠的写区）；
2. 有**独立的下一个动作**（不是同一条线上的一前一后）；
3. 可**独立验证**（有自己的门禁命令 / 验收标准）。

典型来源：不同开发者；同一仓的不同子项目（`backend/` `admin/` `h5/`）；同一人但明确隔离的并行线。

**判定**：轨道数 ≥2 → 多轨。多轨项目**必须显式写出「角色/责任线 → 轨」映射**，否则读者无法路由到自己的那一份。

### 04.2 目录形态

```
docs/
├── active-context.md      ← 薄索引与路由表（≤50 行）
├── tasks.yaml             ← 任务看板**唯一源**：轨→模块→任务 + 状态/面向/类型/负责/依赖（见 §05）
├── tasks-html/index.html  ← 由项目 `scripts/` 生成的任务看板（离线单文件，**勿手改**）
├── context/
│   ├── <轨A>.md           ← 轨 A 台账（≤100 行）
│   └── <轨B>.md           ← 轨 B 台账（≤100 行）
└── archive/
    └── <拆轨前看板>.md     ← 原看板全文冻结快照（不删信息）
```

- **轨文件按责任域命名**（`backend` / `admin` / `h5` / `web` / `mobile` …），**不要按人名**——人换岗位、轨不变。
- **归档不是删除**：拆轨时把原看板**全文冻结**存档（含完成纪要、验证证据等 git 里复原不了的内容），索引只留**里程碑一行 + 指向归档**。
- 本地端口登记等**跨轨共享信息放索引**（不放某一轨）。

### 04.3 模板：`docs/active-context.md`（薄索引）


### 04.5 共享面不属于任何一轨

跨轨共享文件（契约产物、字段字典、对接单等）**不归属任何一轨**，只在**基线轨**（通常＝产出该共享物的那一轨）改动，且**改动前先在 `docs/tasks.yaml` 登记**。这样「谁动了共享契约」永远有一处集中可见。

### 04.6 与就地入口（子目录 `AGENTS.md`）的关系

可在子项目目录（如 `admin/AGENTS.md`、`h5/AGENTS.md`）放**纯导航**入口（≤15 行：指向索引 + 本轨文件 + 本轨门禁命令）。**规则本体仍单源在 `docs/PROJECT-RULES.md`，导航文件不得复制规则**——否则会形成第二份必然漂移的规则。好处是：AI 工具按就近原则加载子目录入口，一步落到本轨，无需先读全量规则。

## 05. 任务看板：`docs/tasks.yaml` → 生成的 HTML（多任务 / 多轨时启用）

> **触发时机**：任务数较多，**或**轨道数 ≥2，**或**需要「多级分类 + 依赖 + 可视化进度」。**极小项目不必建**——任务写在索引/轨看板即可，别为仪式感建文件。

### 05.1 单一源 + 派生看板（防双写的关键）

- **唯一源 = `docs/tasks.yaml`**：全量任务（**含单轨内部**），三级树 轨 → 模块 → 任务。
- **派生物 = 单文件 HTML 看板**：由项目 `scripts/` 里的脚本生成，**禁止手改 HTML**；改 YAML → 重跑脚本。
- **各轨看板不再抄任务清单**：轨看板只留「本轨目标 / 本轨下一步 / 本轨关键决策」。**一件事只有一个权威位置**——任务状态只在 YAML。
- 索引 §03 **不重复**任务表，只留一行指针。

### 05.2 数据模型（字段）

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | **稳定编号、只增不改**。跨轨/非轨沿用 `D-xx`；轨内用 `<轨前缀>-xx`（如 `BE-` `AD-` `H5-`） |
| `title` | ✅ | 任务标题（允许 `**重点**` 粗体） |
| `status` | ✅ | `done` 已完成 / `doing` 进行中 / `blocked` 被阻塞 / `todo` 未开始 |
| `face` | | 面向：管理端 / 用户端 / 跨端（与所属轨同义时可省，避免重复标签） |
| `type` | | 类型：开发 / 文档 / 联调 / 运维（**文档类任务要能表达"还没设计"**） |
| `owner` | | 负责人（`@someone` / 待定 / 业务方 / 公司侧） |
| `created` | ✅（新任务） | 创建日期（YYYY-MM-DD；历史任务可补）——燃尽图依赖此字段 |
| `date` | | 完成日期（仅 done 填） |
| `dep` | | 依赖（挡住它的任务 ID，列表） |
| `inferred` | | `true` = 推断项，看板标 ⚠ 待确认（★ 反向生成时必用） |
| `note` | | 证据 / 说明（尽量带可核验出处） |

另需顶层 `milestones`：项目级阶段（名称 / 归属轨 / 状态 / 门禁），给「横跨各轨的总进度」一个落点。

### 05.3 生成器要求

- **单文件、离线可双击**（内联 CSS/JS、无外链）：可截图、可直接转发。
- **不依赖 JS 渲染内容**：卡片/列表由脚本生成，JS 只做视图切换与筛选——避免"JS 挂了就白屏"。
- **四视图**：**概览**（默认视图）/ 按状态看板 / 层级树 / 模块 × 状态矩阵；**筛选**：轨 / 模块 / 状态 / 面向 / 类型 / 负责人 + 关键字。
- **概览视图**：项目信息环形图（完成率 / 按轨分布 / 按类型分布）+ 燃尽图 + 里程碑进度表。**燃尽图**按任务 `created` / `date` 推导——总量线、剩余线、当日新增柱；无计划目标日期时不画理想线。**里程碑进度口径**：已完成里程碑恒 100%（轨内后续新增任务不追溯旧里程碑）；未完成的按归属轨任务完成率估算（跨轨里程碑按全项目）。
- **进度概览**：总数 + 各状态计数 + 完成率；项目级阶段另做一条里程碑条。
- 长列表要**给状态列限高内滚**，别让页面变成几千像素高（否则"一眼看全局"就废了）。
- 生成器脚本放项目 `scripts/`，用轻量运行时（Python 即可），**不引重量级依赖**。
- **参考实现**：技能自带 `assets/build-tasks-html.py`（仅依赖 PyYAML，符合上述全部要求），复制到项目 `scripts/` 即用，项目可按需裁剪。

### 05.4 约束

- **编号只顺延、不重编号**（全仓常有多套引用：`Q-` / `R-` / 坑号 / 切片号，重编号会集体断链）。
- 完成节点 → 改 YAML 状态（+ 更新本轨「下一步」）→ 重跑生成器。
- 反向生成初始数据时，**推断项一律标 `inferred: true`**，交给用户逐条确认，不要假装是既定事实。
